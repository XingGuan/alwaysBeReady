# 记一次：克隆的仓库里看不到新分支？其实不是 bug，是设计

## 1. 先说我当时是怎么“懵”的

事情是这样的：我在 GitHub 上 fork 了一个项目，然后 `git clone` 到本地，开始愉快地改代码。过了几天，原仓库作者推了一个新分支，我这边死活看不到——GitHub 网页上没有，本地 `git branch -a` 也扫不到。

我当时第一反应是“我 fork 漏了？”，甚至想删掉重新 fork 一遍。后来才明白，**fork 那一刻，它只复制了当时存在的分支**；之后原仓库新增的分支，不会自动飘到你那边去。而 `git clone` 默认也只检出默认分支（比如 `main`），其他分支的信息虽然下载到了本地，但 Git 不会自作主张帮你创建这些分支的本地版本。

说白了，这不是 bug，是 Git 刻意保持的“冷静”——**它只做你明确让它做的事**。但冷静过头，就让人困惑了。

---

## 2. 核心解法：`upstream` 这个“别名”到底在帮什么忙？

要解决这个问题，绕不开 `upstream`。我当时看到教程里都写 `git remote add upstream ...`，我当时的理解是这不就加个远程别名吗，但它的实际作用比我想象的大。

你可以把 `upstream` 理解成给“原作者仓库”在本地起的一个昵称，本质上是一个 URL 快捷方式。它的三个实际用途，我越用越觉得设计巧妙：

- **第一，它是“数据源头”**。只要配置一次，之后想同步最新内容，只需要 `git fetch upstream`，不用再翻浏览器去复制原仓库地址。省事。
- **第二，它天然区分了“我的”和“他的”**。`origin` 通常指向你自己的远程仓库（有写权限），`upstream` 指向原作者的仓库（通常只能读）。这个命名约定让协作关系一目了然，而且万一你手滑 `git push upstream`，会因为权限不足被拒绝——反而成了一道安全防线。
- **第三，它提供了一个明确的合并基准**。当你需要把原仓库的最新改动合到本地时，`git merge upstream/main` 这种命令读起来就很清晰：“我要合并来自 upstream 的 main 分支”。

> 一个小细节：`upstream` 只存在于你电脑的 `.git/config` 文件里，GitHub 页面上看不到，别人也不会受影响。它就是个本地“记忆卡”。

---

## 3. 实际怎么操作？我一般按需求二选一

如果你也遇到这情况，不用慌，下面两种方式我都用过，具体选哪个看你的目的。

### 方案一：只同步我需要的某几个分支（精细化操作）

大多数时候，我并不想要原仓库的所有分支，只想要那个新增的 `feature/xxx` 或 `hotfix`。这种情况下我会这样：

```bash
# ① 添加 upstream（只需一次）
git remote add upstream git@github.com:原仓库地址.git

# ② 拉取原仓库所有分支的元数据（这一步不会动你的工作区文件）
git fetch upstream

# ③ 在本地创建并切换到你想要的那个分支，基于 upstream 的对应分支
git checkout -b <本地分支名> upstream/<远程分支名>

# ④ 推送到我自己的 origin，并设置上游跟踪，以后直接 git push 就行
git push -u origin HEAD
```

这里 `-u` 参数我一开始总忘，后来养成习惯加上，省得每次都要指定远程分支。

### 方案二：把 upstream 的分支“搬”到我的远程（批量或单个都行）

> 补充：原标题为“一次性把 upstream 的所有分支‘搬’到我的远程（省事粗暴）”，改成了更准确的表述，因为下面既讲了批量也讲了单个。

有时候我想让自己的 fork 和原仓库完全一致，包括所有分支，但又不想在本地一一创建。这时候可以用一条“引用映射”命令，我当时第一次看到时也怀疑“没本地分支也能 push？”，试过之后才发现真的行：

```bash
# 同样先 fetch 全部信息
git fetch upstream

# 把 upstream 下的所有远程引用，原样推到 origin 的 heads 下
git push origin 'refs/remotes/upstream/*:refs/heads/*'
```

> 如果远程已有同名分支且冲突，且你确定要用 upstream 覆盖，就加 `-f` 强制推送：
> ```bash
> git push -f origin 'refs/remotes/upstream/*:refs/heads/*'
> ```

> **补充：如果只想同步某一个特定分支怎么办？**  
> 比如原仓库新增了 `dev` 分支，你只想同步这一个，而不是全部，那么命令会更具体一些：
>
> ```bash
> git push origin refs/remotes/upstream/dev:refs/heads/dev
> ```
>
> 这条命令的完整含义是：“把我本地缓存的 `upstream/dev` 分支（即上游仓库的最新代码），作为一个纯粹的提交快照，直接推送到我的 `origin` 远程仓库的 `dev` 分支上。”
>
> 为什么要写这么长一串 `refs/remotes/` 和 `refs/heads/`？因为 Git 默认去 `refs/heads/` 下找本地分支，而 `upstream/dev` 是存储在 `refs/remotes/` 下的远程跟踪分支，不写全路径 Git 会报错。写了全路径，就相当于告诉 Git：“别猜了，我给你的就是绝对路径。”  
> 而方案二里带 `*` 的通配符命令，无非是把这条规则批量应用到了所有分支上。

#### 我当时的一个疑惑：本地没分支，真的能 push 到远程？

能。因为 `git push` 推送的核心是**提交对象**和**引用**，不是“分支”这个抽象概念。当你 `git fetch upstream` 之后，原仓库的所有提交已经完整下载到你本地的 `.git/objects` 目录里了，`refs/remotes/upstream/*` 这些引用就是指向这些提交的“指针”。  
`git push origin A:B` 的意思就是“把本地 A 位置指向的那个提交，推送到远程的 B 位置”。所以即使本地没有 `dev` 分支，你也可以直接写：
```bash
git push origin refs/remotes/upstream/dev:refs/heads/dev
```
方案二里的 `*` 通配符不过是把这一条规则批量应用了而已。想通了这一点，就不再觉得“神奇”了。

---

## 4. 两个小细节，顺便提一嘴

- **`HEAD` 是什么**：它就是“当前所在分支”的快捷方式。`git push origin HEAD` 就是“把我现在正在改的这个分支推上去”。省得打分支名。
- **`git fetch` 真的不会动你代码**：它只更新本地缓存里的远程引用，不会修改你工作区的任何文件。只有你执行 `checkout` 或 `merge` 之后，文件内容才会变化。所以放心跑。
- **这个问题不限于 GitHub**：GitLab、Gitee、自建 Git 服务器都一样，因为这是 Git 本身的机制，和平台无关。

---

**最后，用一句我自己的话总结**：  
`fork` 和 `clone` 都只做了“当时那一刻”的事，后续的增量需要你主动去“拉”和“推”。`upstream` 就是那条连接源头的小路，而 `fetch + push` 就是你在路上来回搬运的动作。理解了这个逻辑，以后遇到“少分支”的情况，就不会再懵了。
